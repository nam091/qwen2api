  sau khi invalidate.

  if cacheHit {                                                                 
      // ... invalidate keys ...                                                
      cacheHit = false                                                          
      // ❌ Không có: chatID = ""                                               
  }

  cacheHit = false                                                              
  chatID = ""      // ✅ Clear chatID

  🔴 Vấn đề nghiêm trọng

  1. Race condition: thiếu chatID = "" trong retry loop (chat.go:235-246)

  Phân tích: Đúng. Khi Completions fail và cacheHit == true, code invalidate
  cache keys nhưng không reset chatID. Ở iteration tiếp theo, biến chatID vẫn
  giữ giá trị cũ (đã bị invalidate), và vì chatID != "" nên block if chatID == 
  "" ở dòng 208 bị skip → không tạo chat mới → lại dùng chatID hỏng.

  So sánh với claude_handler.go:349-351 nơi chatID = "" được set rõ ràng sau khi
  invalidate.

  Fix: Thêm chatID = "" sau cacheHit = false ở dòng 245.

  2. Token không được MarkBad đúng cách (chat.go:166-285)

  Phân tích: Đúng. Trong claudeMessages, markBadAndLog chỉ được gọi khi
  shouldRetry(err) && attempt < maxAttempts. Nếu error không retryable hoặc đã
  hết attempt, token xấu không bao giờ bị mark bad. Ngược lại, claude_handler.go
  dùng handleUpstreamFailure luôn mark bad cho auth/rate-limit errors.

  Fix: Thay writeClaudeError bằng pattern tương tự handleUpstreamFailure — kiểm
  tra upstream error type và mark bad trước khi return.

  3. lookupConvKeyCached luôn recompute (claude_handler.go:799-816)

  Phân tích: Đúng. Comment nói optimization tránh gọi collapseMessages lần 2,
  nhưng thực tế dòng 815 luôn gọi collapseMessages(prefix). Function này không
  có lợi ích gì so với lookupConvKey.

  Fix: Hoặc xóa function và dùng lookupConvKey trực tiếp, hoặc implement
  optimization thật sự (dùng prefix của fullCollapsed khi msgs[:-2] khớp). Vì
  fullCollapsed là collapse của toàn bộ messages (bao gồm trailing
  assistant+user), nó KHÔNG phải là prefix hash → optimization mô tả trong
  comment là sai về mặt logic. Tốt nhất là xóa function này và dùng
  lookupConvKey.

  4. Tool call index calculation phức tạp (chat.go:627-633)

  Phân tích: Đúng. Nhánh 3 (if cleanText != "") luôn ghi đè nhánh 1 khi
  cleanText != "", làm nhánh 1 chỉ có tác dụng khi cleanText == "" && 
  !thinkingStarted. Logic nên viết lại thành if/else rõ ràng.

  Fix: Viết lại thành:

      toolStartIdx = textBlockIdx + 1
  }

  5. emittedLen tracking bằng byte count (chat.go:506-514)

  Phân tích: Có rủi ro nhưng không nghiêm trọng. Code đã có safe boundary
  calculation lùi safe xuống UTF-8 rune start (dòng 507-509). Phần text giữa
  emittedLen và safe sẽ được emit ở chunk tiếp theo. Tuy nhiên, nếu thinking
  block xen kẽ giữa các text chunks, emittedLen không được update trong thinking
  phase → có thể dẫn đến duplicate khi quay lại text phase.

  Fix: Đảm bảo emittedLen chỉ track text bytes (không tính thinking), và khi
  chuyển từ thinking sang text, reset tracking nếu cần. Hiện tại code đã tách
  biệt fullContent (text only) và fullThinking, nên emittedLen trên fullContent
  là đúng. Rủi ro thực tế thấp.

  6. Non-streaming path thiếu FixMalformedToolCalls (claude_handler.go:773-792)

  Phân tích: Đúng. aggregateClaudeResponse deobfuscate tool names nhưng không
  gọi FixMalformedToolCalls như streaming path.

  Fix: Không thể fix dễ vì non-streaming path không có cont (Continuer) — nó cần
  token và chatID để gửi request sửa. Cần truyền thêm context hoặc chấp nhận
  limitation này. Ưu tiên thấp vì hầu hết Claude clients dùng streaming.

  7. Continuation request không preserve thinking mode 
  (claude_handler.go:857-871)

  Phân tích: Đúng. buildContinuationRequest copy req bằng out := req (shallow
  copy struct), nên EnableThinking pointer field VẪN được giữ nguyên (cùng
  pointer). Vấn đề không tồn tại — Go struct copy giữ nguyên pointer fields. Trừ
  khi ai đó nil-out EnableThinking sau đó, flag vẫn được preserve.

  Kết luận: False positive. Không cần fix.
